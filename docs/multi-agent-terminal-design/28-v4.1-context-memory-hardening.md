# v4.1 Context and Memory Utility Hardening

> **Historical v4.1 design record.** Superseded for current authority by v4.1.1 documents 32–34 and `V4.1.1-CHANGELOG.md`.

## 1. Why v4.1 exists

v4.0 established strong memory authority, provenance, lifecycle, retrieval trace, and benchmark foundations. Its remaining risk was imbalance: the package was precise about how memory is governed, but less precise about whether a memory is useful, whether current state should be represented as memory, and how obsolete experience becomes ineligible automatically.

v4.1 keeps the v4.0 safety baseline and changes the cognitive center of gravity from “store governed memory” to “resolve current state, retrieve evidence, and use measured experience only when it adds value.”

## 2. Main changes

### 2.1 Three-store architecture

- Authoritative State Store for current instructions, overrides, decisions, settings, and preferences.
- Evidence Store for repository source, artifacts, events, decisions, receipts, and verified outputs.
- Experience Memory Store for episodes, semantic lessons, procedures, and negative memory.

### 2.2 Executable invalidation

New v4.1 memory proposals use typed invalidation rules. Retrieval requires a current passing evaluation for every declared rule.

### 2.3 Shadow promotion

Model-generated semantic, procedural, and negative memory cannot receive deterministic or policy approval without a passing equal-input shadow comparison. User approval remains an explicit auditable override.

### 2.4 Utility and consolidation

Immutable usage events and rebuildable utility snapshots measure contribution, harm, redundancy, and token cost. Consolidation creates retained actions and new versions rather than deleting history.

### 2.5 Adaptive context

Context allocation is based on task class, risk, information-need coverage, contradiction, marginal utility, and cost. Static percentages are fallback profiles only.

### 2.6 Controlled benchmark arms

Benchmark v2 isolates the value of compaction, evidence retrieval, and experience memory through four equal-input experiment arms.

## 3. What remains intentionally unproven

- production retrieval precision and recall;
- production quality improvement;
- optimal utility-score weights;
- model-judge reliability;
- real p95 latency on representative repositories;
- autonomous consolidation safety;
- remote retrieval containment on installed Windows builds.

These remain runtime release gates, not design claims.

## 4. MVP reduction

The first runtime slice is limited to state, evidence, negative/procedural memory, typed invalidation, immutable context, contribution events, and controlled benchmark arms. Broad semantic extraction, preference inference, remote retrieval, and autonomous consolidation are deferred.
