# v4.1.1 Loop Review Report

## 1. Review method

The v4.1 package was reviewed in repeated adversarial loops. Each loop followed the same rule:

1. identify a concrete bypass, contradiction, or unprovable claim;
2. add a regression test that fails for the specific reason;
3. change the smallest normative contract set;
4. rerun v4.1.1 checks and every historical regression suite;
5. repeat until no unresolved critical or important structural finding remained.

This report concerns contract integrity. It is not evidence that production agents retrieve better context or solve tasks more accurately.

## 2. Critical and important findings closed

| Finding | v4.1.1 resolution |
|---|---|
| New v4.1 definitions were not all reachable from the cognitive schema root | Cognitive schema v3 exposes state, conflict, invalidation, shadow, usage, consolidation, origin, arm, binding, and budget records through top-level `oneOf` |
| Active state could be future-dated or already expired | New state must be active and valid at creation time; resolution rechecks validity at decision time |
| Equal-precedence divergent state could be silently selected | Resolution is rejected until an explicit conflict record exists |
| Recorded conflicts could not be resolved cleanly | Resolution receipt now carries an explicit conflict foreign key; candidate sets and timestamps must match |
| Multiple receipts could resolve one conflict | Partial unique index permits only one non-null receipt per conflict |
| Migrated terminal state lost an explicit end timestamp | Migration deterministically backfills `ended_at` from lifecycle time |
| Invalidation accepted object-shaped but unsupported rules | SQL validates allowed kind, cadence, unique rule ID, and kind-specific payload |
| An unrelated task evaluation could block or authorize retrieval | Retrieval selects the latest evaluation applicable to the current task/project and not later than retrieval start |
| Future invalidation evidence could authorize an earlier retrieval | Eligibility requires `evaluated_at <= retrieval.started_at` and unexpired validity |
| Memory could enter a context package without passing retrieval eligibility | Every memory context item must bind the exact selected retrieval candidate |
| A selected candidate from an older run of the same task could be reused in a different context package | Context admission now requires the candidate retrieval session, agent run, and context package to be the same preallocated run |
| Shadow rows were not bound to actual experiment arms or exact candidate memory | Immutable arm records and one-memory candidate bindings are required |
| A legacy unbound `passed` shadow could authorize promotion after migration | Promotion independently rechecks arm and memory isolation; legacy rows are not grandfathered |
| Concurrent shadow timestamps allowed ambiguous “latest” selection | Evaluation time is unique per memory; promotion also rejects ambiguous legacy maxima |
| Shadow pass ignored cross-scope and stale-memory regressions | Both counters are required and must be zero for `passed` |
| Shadow requirement did not distinguish origin | Model-generated and legacy-unknown durable lessons require shadow for policy/deterministic promotion; explicit user/approved/imported origins remain auditable exceptions |
| An origin exception could be asserted without proving who or what created it | Every origin now binds coherent actor kind/ID, actor-binding digest, and exact in-scope artifact evidence/digest |
| A legacy or already-verified memory could receive a new origin exemption after review | Origin can be written only while memory is `candidate`; verification requires origin, while migrated verified memory remains origin-less/legacy-unknown and cannot be reclassified |
| Usage events did not prove which retrieved or included item contributed | Included and downstream usage binds both the exact retrieval candidate and context package item from the same run/package with coherent boolean implications |
| Consolidation could claim application without the corresponding lifecycle/relation effect | Apply transition verifies actual stale/retract/supersede/merge effects; application time is set-once |
| `split` was under-specified | Autonomous split is rejected and deferred rather than represented by a false single-result contract |
| Context allocations could use real values or exceed the true window after reserves | Allocation values are integers, sum exactly, and allocation + output reserve + verification reserve cannot exceed declared maximum |

The final contract set passes:

- `79/79` v4 cognitive checks;
- `30/30` v4 traceability checks;
- `30/30` v4.1 memory-utility checks;

- `97/97` full package checks.

Clean v5 installation and v4→v5 migration expose the same `382` explicit tables, indexes, triggers, and views in the seeded structural comparison.

## 4. Remaining limitations

The review deliberately leaves these claims unproven:

- retrieval precision, recall, and source coverage on representative repositories;
- improvement over no-memory and compaction-only baselines;
- causal accuracy of per-memory outcome deltas;
- evaluator/model-judge reliability;
- appropriate utility weights and retirement thresholds;
- p95 latency, token overhead, and storage growth;
- safety of autonomous merge/supersede decisions;
- Windows installed-binary containment and crash recovery.

These are runtime gates. Passing this package means the proposed records and transitions are harder to misuse; it does not mean the product has achieved top-tier agent quality.

## 5. Recommendation

Implement only the state/evidence/negative-procedural-memory vertical slice first. Run the four controlled benchmark arms before expanding semantic extraction, preference inference, automated consolidation, remote retrieval, or cross-project memory.
