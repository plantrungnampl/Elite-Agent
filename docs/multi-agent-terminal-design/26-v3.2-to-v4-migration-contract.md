# v3.2 to v4.0 Cognitive Memory Migration Contract

## 1. Objective

Migrate v3.2 authority records into the v4.0 cognitive model without treating legacy summaries, status labels, vector scores, or model assertions as stronger evidence than they actually are. The migration preserves reconstructible history, quarantines ambiguity, and rebuilds all disposable indexes from authoritative sources.

## 2. Preconditions

The migration starts only when all of the following are true:

- the installed authority database matches the exact reviewed `schemas/sqlite-v2.sql` checksum;
- the v3.2 core and hardening suites pass against a copy of the database;
- a SQLite online-backup artifact and Artifact Store manifest have matching verified digests;
- ordinary application writes are paused and one migration owner holds the maintenance fence;
- the migration binary, v2 and v3 schema digests, application version, policy snapshot, and start time are recorded;
- sufficient free disk space exists for the backup, migrated database, rebuilt indexes, and rollback reserve.

A checksum mismatch is not auto-upgraded. It enters manual migration review.

## 3. Schema installation

1. Open the v2 database through the verified connection factory with foreign keys enabled.
2. Acquire the maintenance fence and `BEGIN IMMEDIATE`.
3. Apply `schemas/migrate-v2-to-v3.sql` exactly once. The migration installs `memory_entries` insert/update/delete guards in the same transaction, so the legacy source becomes read-only before the schema commit.
4. Run `PRAGMA integrity_check` and `PRAGMA foreign_key_check` before commit.
5. Commit the schema transaction.
6. Compare the resulting `sqlite_master` object set and normalized definitions with a clean `sqlite-v3.sql` database. Any difference aborts cutover.
7. Record the installed schema digest and migration receipt outside the migrated tables.

The SQL migration installs structure only. Legacy memory backfill is a separate, journaled application operation so evidence can be resolved through normal authority ports.

## 4. Deterministic legacy analysis

Before writing `memory_records`, the migrator builds a read-only migration plan.

### 4.1 Identity and version chains

For each connected `superseded_by` chain:

- detect cycles, missing targets, cross-project edges, and duplicate predecessors;
- require one project and one normalized memory type across a valid supersession chain;
- choose the root deterministically by the oldest reachable row, then lexical legacy ID as tie-breaker;
- assign `logical_key = "legacy-chain:" + root_id`;
- assign `version = 1 + distance_from_root`;
- assign new IDs using a documented UUIDv5 namespace over `(project_id, legacy_id)`;
- quarantine cycles, cross-project chains, type-changing chains, and branches that cannot be linearized without guessing.

A standalone row uses `logical_key = "legacy:" + legacy_id` and version `1`.

### 4.2 Memory type mapping

| Legacy value | v4 value | Rule |
|---|---|---|
| semantic/knowledge/fact | `semantic` | Evidence still required for verification |
| procedure/workflow/skill | `procedural` | Success procedure requires verified outcome evidence |
| failure/negative/anti-pattern | `negative` | Failure evidence and applicability required |
| preference | `preference` | Explicit subject and scope required; otherwise quarantine |
| episode/task-history | `episodic` | Must resolve to one project-scoped task/run or remain candidate |
| unknown value | `semantic` candidate | Never auto-promoted |

Working memory is not backfilled into durable `memory_records`; recoverable in-progress state remains in its historical artifacts or becomes a quarantined migration note.

### 4.3 Applicability, subject, and invalidation

Every planned record receives structured `applicability_json`:

```json
{
  "summary": "Migrated legacy memory <legacy-id>",
  "scope": { "kind": "project", "id": "<project-id>" },
  "systems": [],
  "taskClasses": [],
  "repositoryRevisionConstraints": []
}
```

The migrator may narrow the scope to a task only when authoritative references identify exactly one task. It never broadens beyond the legacy project.

Preference memory additionally requires:

```json
"subject": { "kind": "user|project|workspace", "id": "<authoritative-id>" }
```

If the subject cannot be established from explicit legacy evidence, the row is quarantined rather than converted into an active preference.

`invalidation_conditions_json` must contain at least one explicit condition. When legacy data provides none, use the conservative migration condition:

```json
[
  "Any referenced source revision, project scope, or governing policy changes",
  "Applicability has not been independently confirmed after migration"
]
```

This text is a safety condition, not invented domain knowledge.

### 4.4 Origin and sensitivity

- `origin_task_id` and `origin_run_id` are populated only when all resolved references agree on one coherent task/run.
- Otherwise they remain `NULL` and the record stays project scoped.
- `sensitivity` is the maximum classification of the content artifact and all evidence sources.
- A missing or unresolvable content artifact quarantines the record.
- `confidence_millionths` is copied as advisory metadata only and never acts as verification or promotion proof.

## 5. Evidence reconstruction

Each legacy `source_refs_json` entry is parsed independently.

A v4 evidence link is created only when:

- the source exists;
- source and memory belong to the same project;
- the referenced revision is known;
- the current authoritative digest matches the legacy or reconstructed digest;
- the relationship can be classified without model inference.

Malformed, missing, stale, or cross-project references are recorded in the quarantine report. They are not silently dropped from an otherwise verified record.

Legacy `verification_method` is descriptive only. A record may transition to `verified` only when at least one current `supports` or `verifies` evidence link exists.

## 6. Backfill write sequence

Every migrated row is inserted through the v4 authority lifecycle as `candidate`, even when the legacy row says `active`.

For each planned record, in deterministic chain/version order, first resolve active-version conflicts. A valid logical chain may end with at most one active destination version. When multiple legacy rows claim `active`, only the newest evidence-valid and review-valid version may be selected; older coherent versions are related and terminalized as `superseded`. Tied, branched, or otherwise ambiguous active claims are quarantined rather than chosen by guesswork.

1. persist the content and migration-plan artifacts;
2. insert `memory_records` with `status='candidate'`, `created_at` copied when valid, and `status_changed_at=created_at`;
3. insert validated evidence links;
4. apply the status mapping below through normal transitions;
5. insert supersession relations from newer to older records;
6. terminalize older records as `superseded` only after the required newer relation exists;
7. append a per-record migration receipt containing source ID, destination ID, mapping decision, evidence IDs, status transitions, and quarantine reasons.

### 6.1 Status mapping

| Legacy status | v4 sequence |
|---|---|
| `candidate` | remain `candidate` |
| `verified` | `candidate → verified` only with current supporting evidence; otherwise remain candidate |
| `approved` | verify, then create a migration promotion review and `verified → approved`; otherwise remain candidate |
| `active` | verify, create review, approve, then activate; otherwise remain candidate |
| `rejected` | `candidate → rejected` |
| `retracted` | `candidate → retracted`, retaining migration reason evidence |
| `superseded` | create the newer `supersedes` relation, then `candidate → superseded`; quarantine if no coherent newer version exists |

A migration promotion review is permitted only when its receipt binds:

- the exact legacy row and destination memory ID;
- the verified schema/migration digest;
- current supporting evidence IDs and hashes;
- the legacy approval actor when authoritative, otherwise the migration policy identity;
- the decision time and migration operation digest.

The review does not claim that a model-generated legacy summary is true. It only attests that the legacy authority and current evidence satisfy the v4 transition policy.

## 7. Derived state rebuild

Do not import the following as authority:

- vector values, ANN indexes, or vector-engine scores;
- reranker scores and retrieval ranks;
- inferred graph edges without source evidence;
- caches or temporary summaries;
- model-generated summaries solely because their legacy status was active.

Create an `index_generations` record in `building`, rebuild exact/FTS, vector, graph, episodic, procedural, and negative-memory projections from authority records, persist a source-manifest artifact, run canary isolation checks, and then transition the generation to `current`. Completion evidence is set once.

## 8. Quarantine

Quarantined rows remain readable through a migration report but are not inserted as active memory. Each quarantine entry contains:

- legacy ID and project;
- reason code;
- conflicting/missing reference IDs;
- source row digest;
- recommended operator action;
- whether a safe candidate-only import is possible.

Reason codes include `cycle`, `cross_project_reference`, `missing_content`, `invalid_supersession`, `unknown_subject`, `unverifiable_status`, `malformed_source_refs`, and `sensitivity_unknown`.

Operators may repair source data and rerun a new idempotent backfill attempt. They may not edit completed migration receipts.

## 9. Failure and rollback

### Before schema commit

Rollback the transaction. The v2 database remains authoritative.

### After schema commit but before first v4 backfill receipt

Restore the verified backup or retry the idempotent backfill after correcting the cause.

### After v4 backfill receipts exist

Do not reactivate legacy writes. Resume from the journal using deterministic destination IDs and per-record compare-and-set. A failed index build leaves authority data intact and the application in degraded exact/keyword mode with the generation marked `failed`.

Rollback to v3.2 after accepting v4 writes requires an explicit reverse-migration product decision; it is not an automatic recovery path.

## 10. Acceptance evidence

Cutover is accepted only when:

- legacy `memory_entries` rows remain readable, while post-install `INSERT`, `UPDATE`, and `DELETE` attempts are rejected;
- artifact retained-delete, identity-replacement, availability, and verification guards are installed with definitions identical to the clean v4 schema; metadata deletion, identity reset, quarantine resurrection, and rejected-to-approved promotion are rejected;
- `retrieval_sessions` accepts traced terminal `indeterminate` and retains terminal receipts;
- legacy row count equals migrated + safely skipped + quarantined counts;
- deterministic ID and version mappings are unique and reproducible;
- clean-install and migrated databases have identical normalized schema objects;
- `integrity_check` passes and `foreign_key_check` returns no rows;
- no cross-project evidence, relation, retrieval, or context reference exists;
- every active migrated record has current verification evidence, a granted review, an atomic non-expired activation timestamp, and is the only active version of its project/logical key;
- every `superseded` record has a newer linked version;
- preference memory has an explicit subject and scope;
- all retained v3.2 context packages remain reconstructible;
- denied canaries are absent from every new index branch;
- index loss/rebuild does not remove authority records or receipts;
- v3.2 regression, v4 cognitive, traceability, migration, and full package suites pass.
