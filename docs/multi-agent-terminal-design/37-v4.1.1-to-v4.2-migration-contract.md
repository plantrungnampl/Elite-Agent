# v4.1.1 to v4.2 Migration Contract

## Source and target

- Source clean-install authority: `schemas/sqlite-v5.sql`.
- Target clean-install authority: `schemas/sqlite-v6.sql`.
- Upgrade script: `schemas/migrate-v5-to-v6.sql`.

The migration is additive except for four drifted terminal-run triggers, which
are dropped and recreated with the six canonical terminal statuses.

## Added authority

- actor bindings, credential challenges, and proof bindings;
- trusted workflow profile/outcome/phase authority;
- deliverable/workspace acceptance and completion packages;
- exact final-commit verification receipts;
- canonical memory wire and preference-subject bindings;
- logical benchmark suite/case versions;
- exact benchmark run/comparison receipts and quality release decisions.

## Compatibility rules

1. v5 events, artifacts, approvals, memories, benchmark rows, and audit history
   remain retained and immutable.
2. New v4.2 workflow decisions use `task_workflow_authority`; legacy task phase
   is not sufficient authority.
3. New memory proposals require cognitive-memory v4 canonical bindings before
   verification. Existing v5 memory remains readable but cannot be silently
   reclassified as v4 canonical wire data.
4. New quality comparisons use v6 benchmark receipt tables. Existing v5
   comparisons cannot authorize a v4.2 quality claim.
5. Existing approval receipts remain audit evidence. New granted approvals
   require actor/challenge proof before the approval state resolves.

## Verification

The migration is accepted only when:

- foreign-key and integrity checks pass;
- clean v6 and migrated v5 databases expose the same non-internal SQLite object
  set;
- all historical suites pass;
- the v4.2 terminal, workflow, benchmark, memory round-trip, actor replay, and
  traceability checks pass.
