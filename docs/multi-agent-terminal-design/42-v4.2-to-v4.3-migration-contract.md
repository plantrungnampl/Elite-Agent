# v4.2 to v4.3 Migration Contract

## 1. Scope

`schemas/migrate-v6-to-v7.sql` upgrades the exact v4.2 SQLite v6 contract to v4.3 SQLite v7. It is additive except for replacement of the three v4.2 workflow phase-update triggers with event-authority triggers. Historical rows and historical schemas remain retained.

## 2. Preconditions

Before migration:

1. the database must satisfy `PRAGMA integrity_check = ok` and return no rows from `PRAGMA foreign_key_check`;
2. the deployed schema must match the reviewed `sqlite-v6.sql` object signatures;
3. no task workflow transaction may be active;
4. the application must be stopped or in a migration-exclusive mode;
5. a file-level database backup and artifact-store checkpoint must exist.

## 3. Added authority

The migration adds:

- normalized transition rule tables populated from workflow v3;
- immutable transition events, guard bindings, and effect bindings;
- workflow stream version and accepted-event pointer;
- immutable profile-revision receipts and monotonic escalation enforcement;
- exact run-configuration bindings;
- assurance degradation receipts;
- v7 workflow projection and immutability triggers.

Existing v6 workflow rows receive `stream_version=0`, `profile_revision=1`, and null last-event/revision pointers. Their current phase/profile/outcome remains unchanged. The next phase change must use v7 event authority.

## 4. Transaction and failure semantics

The migration runs inside one immediate transaction. Any statement failure rolls back the complete migration. A partially created v7 schema is not a supported state.

After migration, application startup must compare the clean v7 and migrated-v7 object signatures expected by the release. The included validator proves `481/481` object parity for this package.

## 5. Rollback

There is no in-place down migration because accepted transition events and profile revisions are new authority records. Before the application accepts any v7 command, rollback may restore the pre-migration database backup and matching application/artifact checkpoint.

After a v7 command is accepted, rollback means restoring the coordinated backup and replaying/exporting post-backup evidence through an explicit recovery procedure. Dropping v7 tables or rewriting `task_workflow_authority` is forbidden.

## 6. Deployment order

1. stop v4.2 writers;
2. verify database and artifact checkpoint;
3. deploy code that understands v7 but does not start task execution;
4. execute `migrate-v6-to-v7.sql`;
5. run integrity, foreign-key, schema-signature, and package checks;
6. start read-only inspection;
7. enable new transition commands;
8. retain the backup until the release observation window closes.

## 7. Acceptance

Migration is accepted only when clean v7 and migrated v7 have identical non-internal SQLite object SQL, all v4.2 regression suites remain green, v4.3 workflow negative/positive tests pass, and a fresh extraction of the release archive passes package validation.
