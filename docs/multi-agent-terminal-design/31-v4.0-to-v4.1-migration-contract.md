# v4.0 to v4.1 Migration Contract

> **Historical migration contract.** Current installations use `32-v4.1-to-v4.1.1-migration-contract.md` after this step.

## 1. Preconditions

Migration accepts only a database matching the exact reviewed v4.0 `sqlite-v3.sql` authority contract and checksum. Runtime settings must verify foreign keys, WAL, full synchronization, busy timeout, and defensive configuration before migration begins.

## 2. Migration behavior

`schemas/migrate-v3-to-v4.sql` is additive. It:

- preserves all v4.0 authority and cognitive rows;
- installs state, invalidation, shadow, usage, utility, consolidation, and budget tables;
- installs new scope, immutability, eligibility, and promotion triggers;
- adds indexes for state resolution and cognitive analysis;
- does not import or rewrite vector scores;
- does not automatically activate any new state or memory.

## 3. Existing v4.0 memory

Existing memory remains retained. Before it is eligible for v4.1 experience retrieval it must:

1. be represented by typed invalidation rules in a new memory version when the old rule payload is prose-only;
2. receive current passing invalidation evaluations;
3. retain or refresh supporting evidence;
4. satisfy normal active-memory scope and expiry rules.

Migration does not silently reinterpret prose strings as executable rules.

## 4. Preference migration

Existing active preference memory remains historical evidence. The current effective preference is materialized as a `state_record` only after source, scope, and precedence review. No preference is broadened across task, project, workspace, user, or communication surface.

## 5. Benchmark reset

v4.0 benchmark runs remain historical. v4.1 quality comparisons use benchmark schema v2 and four experiment arms. Comparisons cannot mix v1 and v2 case semantics without an explicit compatibility artifact.

## 6. Rollback boundary

Before the transaction begins, create a consistent whole-state backup. If migration fails before commit, SQLite rolls back. After successful migration and new v4.1 writes, rollback to v4.0 requires restoring the compatible backup; v4.0 binaries must not open and mutate a v4.1 database.

## 7. Acceptance evidence

- v3-to-v4 migration installs all required objects;
- existing project/task/artifact/memory rows remain readable;
- clean-install and migrated schemas have equivalent v4.1 objects;
- all historical regression suites remain green;
- new v4.1 negative tests pass;
- package checksums match.
