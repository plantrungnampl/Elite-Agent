# v4.1 to v4.1.1 Migration Contract

## 1. Purpose

v4.1.1 is a governance and integrity patch for the v4.1 context/memory design. It does not claim better agent quality. It closes paths where structurally valid records could bypass applicability, conflict, shadow-isolation, contribution, or token-budget rules.

The normative migration is [`schemas/migrate-v4-to-v5.sql`](schemas/migrate-v4-to-v5.sql). Its only accepted source is the exact reviewed v4.1 [`schemas/sqlite-v4.sql`](schemas/sqlite-v4.sql) contract.

## 2. Preconditions

Before migration:

1. verify the v4.1 schema checksum and application schema version;
2. take a consistent whole-state backup;
3. stop writers and acquire the migration lease;
4. enable and query-verify `foreign_keys=ON`;
5. verify `PRAGMA integrity_check` and the artifact-store reachability manifest;
6. reject migration if local schema drift or unreviewed triggers are present.

## 3. Additive changes

The migration:

- adds `ended_at` to authoritative state and backfills terminal records from `status_changed_at`;
- adds explicit state-resolution conflicts and a one-to-one `conflict_id` link from a resolution receipt;
- adds memory-origin records with coherent actor identity, actor-binding digest, and exact artifact evidence/digest; new records are candidate-only and required before verification;
- adds benchmark arm and exact candidate-memory bindings;
- extends shadow evaluation with cross-scope and stale-memory regression counters;
- extends usage events with exact retrieval-candidate and context-item linkage;
- extends context-budget receipts with total budget and output/verification reserves;
- installs stronger typed-invalidation, retrieval, context inclusion, lifecycle, shadow, usage, consolidation, and budget guards.

No source authority row is deleted or rewritten except the deterministic `ended_at=status_changed_at` backfill for already terminal state records.

## 4. Legacy rows

### 4.1 State

Terminal v4.1 state receives `ended_at=status_changed_at`. Active state remains open-ended. New state must start active and be valid at creation time.

### 4.2 State resolution

Historical non-conflict receipts retain `conflict_id=NULL`. A new equal-precedence divergent resolution must first create an open `state_resolution_conflict`, then create exactly one receipt carrying that conflict ID, then resolve the conflict with that same receipt and timestamp.

### 4.3 Memory origin

Existing memory without a `memory_origin_record` is treated as `legacy_unknown`. Deterministic or policy promotion of legacy-unknown model-like semantic, procedural, or negative memory requires current, correctly isolated shadow evidence.

### 4.4 Shadow evidence

Historical shadow rows are retained but cannot authorize promotion unless their control and candidate runs have v4.1.1 arm bindings and the candidate run binds exactly the evaluated memory. New origin exemptions are never inferred during migration. Existing verified memories remain `legacy_unknown` for gate purposes and cannot be reclassified; only a candidate memory may receive a new actor-binding-digest-and-evidence-bound origin before verification. A historical row is not grandfathered merely because it says `passed`.

### 4.5 Context and utility

Historical usage and budget rows remain readable. New rows must satisfy the v4.1.1 exact-link and bounded-budget requirements. Missing new fields on historical rows are not fabricated.

## 5. Rollback boundary

If the transaction fails, SQLite rolls back. After commit and any v4.1.1 write, rollback requires restoring the pre-migration backup. v4.1 binaries must not write a v4.1.1 database.

## 6. Acceptance evidence

Migration is accepted only when:

- clean `sqlite-v5.sql` and migrated v4→v5 expose the same explicit schema objects and relevant column definitions;
- terminal-state backfill is verified;
- all historical suites remain green;
- v4.1.1 negative and positive transition tests pass;
- package checksum verification succeeds.
