# v4.3 Implementation and Product-Proof Baseline

## 1. Decision

v4.3 is a bounded hardening release. It preserves v4.2 safety, exact-object approval, crash recovery, cognitive-memory authority, and historical contracts. It changes the current implementation authority in four places:

1. every complete normative MAT Agent Control Protocol v2 frame is generated from and validated against a canonical fixture;
2. workflow phase changes require a versioned transition rule, an immutable accepted transition event, required guard evidence, required effects, and an optimistic stream version;
3. provider, adapter, model, policy, budget, fallback, and independence information is frozen in `RunConfiguration v1` without storing credentials;
4. a separate equal-budget benchmark tests whether orchestration provides value beyond a strong single-agent baseline before memory breadth is expanded.

The package remains a design and machine-contract baseline. It does not claim that live models improve outcomes, that every third-party runtime is contained on every Windows build, or that users will adopt the product.

## 4. Workflow authority model

The application reducer is the transition decision authority. SQLite is the invariant boundary.

A trusted reducer executes one transaction:

1. read `task_workflow_authority` at `expectedStreamVersion`;
2. resolve exactly one rule from `workflow-transitions.v3.json` and its normalized SQLite rule rows;
3. verify event, source phase, target phase, profile, outcome, actor/core binding, and task scope;
4. insert the immutable transition command artifact and a `prepared` event;
5. bind every required guard and required effect;
6. change the event to `accepted`;
7. update the workflow projection to the accepted target and increment `stream_version` by one;
8. commit all rows or roll back all rows.

Direct phase updates are invalid. Rejected events are retained and do not consume the stream version; a new command ID may retry the same version after the cause is corrected. Accepted events and profile revisions are immutable and replay-resistant.

## 5. Profile and assurance rules

- `Quick`, `Standard`, `HighAssurance`, and `ReadOnlyResearch` remain the four profiles.
- Escalation is monotonic: `Quick -> Standard`, `Quick -> HighAssurance`, or `Standard -> HighAssurance`.
- A profile escalation is a separate atomic command from a phase transition.
- Downgrade inside the same task is forbidden. A lower-assurance run requires a separately approved child task.
- `ReadOnlyResearch` cannot become write-capable in place; it creates an actor-approved child task with a new outcome boundary.
- High Assurance requires executor/reviewer role separation and at least two policy-defined independence groups.
- When the requirement cannot be met, the task pauses, cancels, or continues only with an immutable degradation receipt and explicit actor proof. The UI must show degraded assurance for the rest of the task.

## 6. Provider and model behavior

A user may operate the product with one configured provider. Multi-provider login is not mandatory. Additional providers improve heterogeneity but do not change core authority.

Fallback is never silent. A different provider or model creates a new run with a new `RunConfiguration`, a new config digest, and a visible reason. `explicit_only` fallback requires user approval. Credential bytes remain in the trusted credential subsystem and are excluded from artifacts, protocol frames, logs, and benchmark receipts.

## 7. Product-proof sequence

The implementation sequence is:

- **S0 Contract repair:** protocol, workflow authority, run configuration, assurance receipt, and package validation.
- **S1 Real read-only vertical slice:** one supported runtime, one repository, Quick profile, evidence, report, cancellation, restart/resume, and Simple Mode.
- **S2 Multi-agent proof:** strong single-agent baselines, Standard cross-review, independent run groups, equal budgets, and paired evaluation.
- **S3 Mediated write:** worktree broker, one fenced executor, structured write/process/test tools, verification, and repair.
- **S4 Exact local commit:** candidate object construction, verification, exact approval tuple, and ref CAS.
- **S5 Evidence retrieval:** exact and FTS retrieval first; vector retrieval only after measured incremental value.
- **S6 Memory and learning:** negative memory first; broader semantic/procedural learning only after isolated benchmark lift.

Fake agents remain deterministic test fixtures. They cannot satisfy the S1 real-runtime gate or the S2 product-proof gate.

## 8. Proof boundary

Passing this package proves that the encoded schemas compile, examples validate, SQLite clean install equals migration, known workflow bypasses are rejected, representative valid commands succeed, protocol examples match fixtures, traceability resolves, links resolve, and no active placeholders remain.

It does not prove model quality, market demand, production sandbox containment, provider availability, pricing stability, or statistically meaningful orchestration lift. Those require runtime evidence and user trials.
